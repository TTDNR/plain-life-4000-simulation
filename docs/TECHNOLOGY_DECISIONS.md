# 技术决策记录

## 0001 Phase 1 审计工具使用 Python 3.12 标准库

日期：2026-09-25
状态：已接受

背景：

需求要求在启动长期模拟前，提交环境资源清单、开局生存核验和初始化一致性检查。没有这些
结果时，长期模拟不能开始。该阶段需要可复算、无网络、无额外依赖的门禁工具。

候选方案：

- 只维护 Markdown，人工检查。
- 使用第三方 JSON Schema、数据框或测试框架。
- 使用 Python 3.12 标准库实现结构化审计。
- 先选择完整模拟引擎，再在引擎内实现门禁。

决定：

Phase 1 使用 Python 3.12 标准库，读取 `data/phase1/*.json` 并输出 Markdown 或 JSON
审计报告。此决定只覆盖长期模拟前的离线门禁，不选择长期运行语言、引擎、数据库或渲染方式。

原因：

- 需求已经明确要求可检查、可复算的三项前置结果。
- 标准库足够完成结构校验、引用校验、汇总和退出码控制。
- 不需要安装包，不污染项目本地依赖，也不引入共享缓存。
- 纯 JSON 输入可以由后续需求方或生成器提供。
- 审计器可以独立替换，不绑定未来模拟实现。

代价和风险：

- 当前不是完整 JSON Schema，字段约束由 `tools/phase1_audit.py` 维护。
- 若要校验大规模逐格世界或 4000 人完整快照性能，可能需要在真实需求明确后更换实现。
- Python 审计器不能承担长期模拟运行时职责。

后续验证：

- 每次修改 `data/phase1/*.json` 后运行单元测试和审计命令。
- 长期模拟引擎选型必须另立决策，记录性能、空间模型、持久化和观察接口的取舍。

## 0002 Phase 1 专项模型使用 Python 3.12 标准库

日期：2026-09-25
状态：已接受

背景：

需求要求在启动长期模拟前生成固定世界和 4000 人初始人口，并核验饮水和食物等基础生存
行为、探索和迁移。当前没有长期帧率、并发规模、交互方式或部署目标，无法据此选择正式
模拟引擎。专项核验必须可复算、无网络，并且不能把测试状态写入正式初始快照。

候选方案：

- 立即选择 Unity、Unreal、Godot 或其他完整模拟引擎。
- 引入 NumPy、Pandas、数据库或第三方代理框架。
- 使用 Python 3.12 标准库实现确定性的短期核验内核。
- 只做电子表格估算，不建立逐日空间消耗模型。

决定：

使用 Python 3.12 标准库实现 `plain_life` 包，包括：

- 100 x 50 的 50 平方公里确定性环境生成。
- 季节、降雨、蒸发、资源再生和消耗。
- 4000 人、1000 家庭的人口与技能初始化。
- 家庭劳动分配、饮水、食物、遮蔽、火、工具、探索和迁移核验。
- Markdown/JSON 报告输出。

该决定不选择长期模拟引擎、数据库、可视化框架或网络架构。

原因：

- 现有需求只要求可检查的开局核验，没有长期性能或交互指标。
- 标准库足以处理当前 5000 格和 4000 人规模。
- 固定种子和状态指纹可以直接复算世界。
- 模型可以随着后续人物决策需求替换，不把测试规则固化为正式模拟器。

代价和风险：

- 当前 365 天专项核验约需两到三分钟，不适合大规模参数扫描。
- 逐家庭规则是简化模型，不能代表完整人类决策。
- 长期代理数量、空间查询和事件频率明确后，可能需要迁移到编译语言、数据引擎或 ECS。

后续验证：

- 当长期模拟需求明确时，另行评估运行时引擎、持久化、性能和多进程方案。
- 在人物决策需求补齐前，不得把本专项模型称为完整人类社会模拟。
- v2 增加版本化输入、逐资源账目、可食比例、个体知识和固定需求/动态生存测试标签；
  v1 基线保持冻结。
- v3 增加季节损失、水具和取火证据、互斥时间账，以及可追溯的个人/家庭短场景引擎。
- v4 将短场景中的家庭分配、局部求助、火种、照护、住所和基础教学接入七天动态循环；
  年度固定压力测试与动态测试使用独立运行标识。
- v5 为食物路径补全世界年内日、资源级候选统计和实际活动，按退出队列解释捕鱼下降，
  并把生态结论前必须隔离的空间可接触性问题写入相容性评估。
- v6 将空间信息拆成有限候选和完整位置信息两个诊断模式，记录发现、迁移和
  迁移前后资源可接触状态；完整信息仅供对照，不进入正式人物规则。

## 0003 S01 继续使用 Python 3.12 标准库并新增 SQLite 执行核心

日期：2026-09-27
状态：已接受

背景：

R1 要求统一时钟、行动生命周期、资源提交、事件记录、快照和个人可见信息。
现有项目已经使用 Python 3.12 标准库实现环境、人口和诊断模型；本轮尚无
外部依赖或长期性能数据要求必须引入 Mesa。

候选方案：

- 立即引入 Mesa 并重写现有环境/人口核心。
- 只保留旧日循环，不建立共享执行核心。
- 使用现有 Python 代码，新增标准库 SQLite 存档与统一核心。

决定：

S01-1 使用 `plain_life/contracts.py` 定义 R1 数据契约，
使用 `plain_life/core.py` 提供唯一时钟、行动生命周期、资源预约、事件日志和
SQLite 存档，使用 `plain_life/core_adapters.py` 连接现有环境/人口状态。
旧诊断基线不删除，尚未接入核心的流程保持明确标记。

原因：

- 现有核心可运行，重写会丢失当前失败基线和已确认语义。
- SQLite 属于 Python 标准库，可以满足可查询事件和恢复需求。
- Mesa 尚未获得必要的代理调度或性能要求，不应为框架名称提前迁移。

代价和风险：

- S01-1 目前是适配层，不是完整生产数据模型。
- 旧 `survival.py` 仍保留独立日循环，直到 S01-2/S01-3 接入核心。
- SQLite 快照大小和 4000 人性能仍需 S01-5 实测。

后续验证：

- 运行 `tools/run_core_contract.py`。
- 在 64 人和 4000 人流程中确认没有第二份时钟或库存。
- 若 Mesa 或数据库性能成为已测量瓶颈，再提交新的技术决策。

## 0004 B/C 接入新 core，旧 survival 诊断独立保留

日期：2026-09-27
状态：已接受

背景：

旧 `survival.py` 的整日循环已经形成 v1—v6 诊断和失败基线，但它同时推进时间、
家庭库存、身体和事件，不能作为新世界的第二个时钟或库存来源。D01 裁决要求
B/C 新行为接入统一 core，旧诊断保持可追溯。

决定：

- 新动作、人物计划、照护、库存和时间只由 `SimulationCore` 推进和提交。
- 旧 `survival.py`、家庭 `food_store` 和分钟日志不进入新运行链。
- 旧环境、人口、无副作用参数和领域计算可以在明确适配层复用。
- 不得把旧整日循环包装成一个 core 回调继续运行。
- 环境每日更新只通过 `WorldClockAdapter` 等模块在 core 时间边界执行，
  恢复时必须重新绑定恢复工厂。

原因：

- 避免双重时钟、双重库存和重复日终身体扣减。
- 保持旧失败基线与新核心结果可分别复现。
- 给 B/C/D 一个明确的写入和只读边界。

后续验证：

- A01—A04 回归通过后，B/C 按 core 动作接口接入三条生活流程。
- 64 人和 4000 人运行使用自己的运行 ID，不复用旧诊断事件。
